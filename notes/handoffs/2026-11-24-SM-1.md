## 2. Behaviour and decisions

- **R-POST-1 / R-POST-5.** `insideBarTimes` starts at `floor(entry / barMs) * barMs + barMs`, so `:00` and `:30` entries are treated the same. `excursions` and `observeTrade` both use it.
- **R-POST-2.** `excursionsFromBars` is unchanged, so fewer than two inside bars gives `null`.
- **R-POST-3.** Stop and target checks use the same inside set. A stop segment starting in the entry bar is checked from the next bar.
- **R-POST-4 / D-H.** `entryBarPassedStop` is true when the entry bar (the matched bar under D-I) traded past the stop in force at entry. Only a complete bar counts, so an open trade's forming bar does not count.
- **Decision: "stop in force at entry."** A strict `stop.from <= entry` check does not work. A stop placed by the entry fill starts at the fill time. For a shifted entry (logged 14:14, matched 14:13) the planned stop's `from` is 14:14, after the matched bar's open. The code therefore accepts a stop with `from <= end of the entry bar` and `to > entry instant`. This is commented in `lib/trade-bar-validation.ts`.
- **D-I.** `observeTrade`'s position windows already start at the matched bar time, so the matched entry bar is the one excluded. Stored `entry_time` is never changed.
- **Not wired in this PR (out of scope):** `components/TradeDetail.tsx` (line ~355) calls `collectDataNotes({...})` and does not pass the new flag. **Until it does, the D-H line will not render in the app.** The fix is one line there: `entryBarPassedStop: observation?.entryBarPassedStop`. The chart is already correct: no finding is pushed, so no flag is drawn.
