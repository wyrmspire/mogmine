## Choices the brief did not cover (reviewer to confirm)

1. **Fresh device with untouched defaults adopts the server copy.** The brief's rule (no base means dirty) would have a new
   device push its defaults over the server's prefs on first sign-in. Added an optional `unedited` value: prefs pass
   `DEFAULT_PREFS`. With no base for the owner, a local value equal to `unedited` is clean. A test covers the plain rule
   (`unedited: null`) so the difference is pinned.
2. **Base kept on a remote-null pull.** The first version reset the base to null here, so the next pull pushed a foreign
   user's value that the first pull had kept. Fixed: `serverFp = foreign ? localFp : baseFp`. A test covers "now or on later
   pulls".
3. **Another user's prefs with no server copy** stay on the device (not pushed), and the device is marked for this owner
   with the base set to the local value. The value is pushed only after the next edit.
4. **Orphan copies** for the singleton use the same `keepOrphans` as store-sync (one slot per key and owner).

## Observations on store-sync.ts (not edited; for the reviewer)

- **Accounts restore leaves the old account active on the server.** `accounts` is archive-only, so a remove returns
  `forbidden`. `store-sync` then marks the id `gone`: this device drops it, but the server row stays active and other
  devices keep it. The UI never deletes accounts, so this only bites on a restore that omits an account. A better fix is to
  push `archived: true` for removed accounts instead of a remove. Test "a restore pushes the restored set" asserts the
  local side only and comments on this.
- **First-sign-in conflict** (open question 1 in the #190 handoff) still applies to trades, accounts, challenges. Prefs
  have the `unedited` rule above.
- **Balance checks have no foreign key** to accounts (`account_id` is a generated column, with a cascade trigger). Checks
  and accounts can push in either order, so no ordering is needed. Verified in
  `supabase/migrations/20261123004734_mogmine_journal_v1.sql`.
