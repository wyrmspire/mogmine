## Behaviour

Refusals (422 `invalid`, nothing written):
- `playbook_id` not an active playbook. The message lists `id ("Name")` pairs. Archived playbooks are refused on write too.
- `account_id` not an active account. Same listing.
- `quick_tags` with any value outside `SETUP_TAGS` ∪ `EXECUTION_TAGS`. The message lists both sets (Q-9).
- `entry_time` or `exit_time` more than 5 minutes after `now` (Q-10, Q-11).
- `risk_cents` not equal to the computed value. This was already a 422 in `journal-commands.ts`; the check is repeated here before the write.

Warnings (201 or 200, saved, `warnings` array always present):
- `playbook_missing`, `setup_tag_missing`, `notes_restate_fields` (HR-1), `stop_moved_without_time` (HR-4), `exit_reason_mismatch` (HR-5), `stated_risk_differs` (HR-7), `price_out_of_range` (Q-10).

Response shape on trade writes: `{ ok: true, data, warnings }`.

## Decisions I took (the prompt left these open)

1. `warnings` sits beside `data` at the top of the envelope, not inside it.
2. The time refusal runs only when `entry_time` or `exit_time` is written, or on create. A note-only PATCH on a legacy trade with a future-dated stored time is not blocked.
3. The playbook and account refusals run only when those fields are written, or on create. The Q-9 tag refusal is the same: a PATCH that does not write `quick_tags` is not blocked by an old tag. A targeted test covers this.
4. `initial_stop_time_defaulted` is in the code union but never emitted. §4 has no row for it.
5. `setup_tag_missing` and the other candidate-based warnings are evaluated on every trade write, including a note-only PATCH. They are informational and never block.
6. If the candidate cannot be built (`normalizeTrade` throws), the checks are skipped and the command layer refuses on its own rules.

## Open item for the planner (out of this package's scope)

`price_out_of_range` cannot fire on the live route yet. `dispatch.ts` has no candle access, and the server-side candle store is only wired in `lib/agent/handle.ts`, which is not in my writable list. The check takes an optional `dayPriceRange` callback through `AgentDispatchOptions`. Until the route handler passes one, the check runs only when a caller supplies a range. The unit test covers both cases. Wiring it needs a one-line change in `handle.ts` (or a read-only bar cache hook) in a later package. The write path must not fetch bars (package prompt §8).
