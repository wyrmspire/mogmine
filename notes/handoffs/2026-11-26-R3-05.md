The capped-page double at `store-sync.test.ts:254` overrides only `repos.trades.list`. Under the spec, `listStored` is now the read source. The real `listStored` returns the short page, so clean local record `a` is dropped and the test fails.

- Fix (outside this package, in `store-sync.test.ts`): have the capped double override `listStored` as well, returning the same filler rows as `{ record, meta: { user_id, created_at, updated_at } }`.

## Deviations and judgment calls

1. **"Adopt the server row via `apply`" is not implemented.** A row in the push set is always dirty against its base, so no "only the base was stale" case can be detected from the stored metadata. After a conflict, the code does one of two things. If the fresh server row already equals the device copy, it converges. Otherwise the device copy is pushed once on top of the fresh `updated_at`. This matches the spec's "if local has unsent edits on top, retry" branch. The server's newer content is overwritten by the device's edit, with no field-level merge. This is the intended last-edit-on-top behaviour, and the planner should confirm it.
2. Singleton conflicts follow the same pattern. A second conflict is reported as `error`, not retried.
