## Merge rules (store-sync.ts `pull`)

1. Local sample, or a `gone` id: kept as it is, never pushed.
2. Local syncable with a remote copy: dirty (fingerprint differs from base, or not in base) keeps local and pushes it; clean takes the remote copy.
3. Local syncable, no remote copy: in base and clean means deleted on another device, so drop it. Otherwise keep and push.
4. Remote only: in base (deleted here while offline) means keep it deleted and push the remove; otherwise add it locally.
5. The new base holds the remote fingerprints (syncable records only). `apply` runs only when something changed. The pull then flushes.
6. Push: a diff against the base, last write wins, no `expectedUpdatedAt`. A refused remove goes into `gone`. Writes and removes stop on `unauthenticated`, `unavailable` or `unknown`.

## Choices the specs did not cover

- **Plural text.** "1 record couldn't sync" for one record, "N records couldn't sync" otherwise. The brief gave only the plural form.
- **`buildBackup` default removed.** It was `trades = state.trades`, which would be an import cycle from `journal-backup.ts`. No caller relies on it; every caller in the repo passes trades.
- **Initial status.** An enabled syncer starts as `syncing` (not `off`), so the header never shows the device text while the first pull is in flight.
- **Online and visibility listeners.** `online` calls `flushNow()` once the first pull has succeeded, and `pull()` before that. `visibilitychange` pulls only when the last pull is over 60 s old.
- **Status on a no-op flush.** When there is nothing to send, the status goes to `synced` and `lastSyncedAt` is refreshed.

## Open questions for the planner / owner

1. **First sign-in conflict.** A device record and a server record with the same id, where this device has never synced that id, are treated as dirty. The device copy wins and overwrites the server copy. This follows the brief's rule, but it can lose a newer server edit when a stale device copy is first uploaded. Decide whether a first sign-in should prefer the server, or ask the owner.
2. **Orphan copies are never restored.** If user A signs out, user B signs in, and then A signs in again on the same device, A's unsynced local records stay in the `orphan:trades:<A>` key. Server data for A comes back from the pull. Only unsynced device-only edits are stuck. Decide whether a restore path is needed.
3. **Refused remove is per device.** `gone` lives in device metadata. Another device that still holds the id will re-push it.
4. **Validation failures retry only on the next change or pull.** That is the brief's rule, which avoids a loop. A record the server will never accept stays in `error` until it is edited.
